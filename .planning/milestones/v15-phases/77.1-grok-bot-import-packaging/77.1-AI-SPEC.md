## 1. System Classification

**System Type:** Code — packaging and developer tooling around the existing Omega Prime MCP host. It is not a new inference system: no model is selected, prompted or judged by anything this phase builds.

**Description:** Make the pushed GitHub repository importable so the default Grok Bot (or a Cursor Teams/Enterprise team marketplace) can set up Omega Prime with the existing Python core attached. Deliverables are declarative manifests (`.cursor-plugin/marketplace.json`, `.cursor-plugin/plugin.json`, root `mcp.json`, a non-secret HTTPS example), one generated `/omega-<name>` command per checked-in skill (27) and routine (7) beside the 12 curated commands, a generator with a drift `--check`, an idempotent stdio bootstrap in the existing shell launcher, frontmatter fixes for 7 skills, and setup/prompting docs. Users are the repository operator, the default Grok Bot that follows the documented setup prompt on its own Linux cloud computer, and Cursor team admins. "Good" means a fresh recursive clone sets up with no undocumented step, the stdio host answers `initialize` and `tools/call omega_command` through the exact declared command with protocol-only stdout, every generated name resolves through `omega_command`, drift fails `--check`, no secret appears anywhere, and every unverified platform behaviour is stated as unproven user UAT.

**Critical Failure Modes:**
1. **Secret exposure.** A bearer token, credential-looking argument or `env` block lands in `mcp.json`, `plugin.json`, the HTTPS example, a generated command file, argv, docs or launcher output. On a Team Bot, teammates can read a Command server's command and arguments (docs.x.ai/grok-bot/team-bots), so this is disclosure, not just a lint issue.
2. **Protocol stream corruption.** Bootstrap output (git, venv, pip, doctor) reaches stdout, or a bootstrap child reads stdin and consumes JSON-RPC frames. The MCP client then fails or hangs, and the failure looks like a platform problem.
3. **Command catalog drift or silent loss.** A generated `/omega-<name>` is unparseable (today's `_COMMAND_RE` accepts one segment), a collision is resolved by dropping or shadowing a command, curated behaviour changes, or `--check` passes while committed files, skills, routines and template disagree.
4. **Unsafe or unrepeatable bootstrap.** The launcher picks a root from cwd, stamps a half-built venv, races a concurrent start, installs unpinned packages, or collapses distinct causes into one exit. An interrupted first start then fails on every later start, or two causes look the same to the operator.
5. **False capability or weakened control.** Docs or manifests claim that Grok Bot loads plugin skills/commands, launches a marketplace-declared stdio server or expands `${CURSOR_PLUGIN_ROOT}`, none of which is verified. Or authentication or approval is relaxed (unauthenticated HTTPS host, a generated command that bypasses `registry.dispatch` approval) to make a route run.

### What Domain Experts Evaluate Against

**Dimension: The declared launch command is safe to show to teammates**

- **Good (domain expert would accept):** `mcp.json` declares exactly one server, `omega-prime`: `type: "stdio"`, `command: "bash"`, `args` = the real script path plus `--bootstrap --transport stdio`. It has no `env`, no `cwd` and nothing credential-shaped. The path (B) command in docs is identical in shape with an absolute path. The HTTPS example carries only a validated `${VAR}` placeholder and an `https://…/mcp` URL. Tokens come from a Bot secret, a mode-0600 token file or the host environment. Argv, examples, launcher output and generated files pass the unchanged secret gate. The single placeholder header is validated by exact shape, not by loosening the gate.
- **Bad (domain expert would flag):** A token, `--token` argument or `env` block appears in a manifest or the documented command. `--token` is suggested for convenience. The secret gate is loosened so the example passes. A Team Bot server silently becomes owner-only because the args "look like a credential". Docs tell users to paste a token into chat.
- **Stakes:** Critical.
- **Source:** CONTEXT constraints. docs.x.ai/grok-bot/team-bots (re-fetched 2026-10-12): teammates "can … read the server's command and arguments, so never put a credential in either". MCP Authorization spec 2025-11-25: stdio implementations "SHOULD NOT" use the OAuth flow and should take credentials from the environment. OWASP MCP Security Cheat Sheet and MCP Security Best Practices: arguments are visible through process listings, and committed `mcp.json` secrets reach every collaborator. `secret_guard.assert_no_secrets` probe (Section 3 pitfall 2).

**Dimension: The protocol stream is clean from the first byte**

- **Good (domain expert would accept):** Spawning the exact declared command yields stdout containing only newline-delimited JSON-RPC messages, from `initialize` through `tools/call`, on cold, warm and failed starts. Bootstrap progress, pip, git and doctor output go to stderr. No bootstrap child reads stdin. Failure before serving exits non-zero with stdout empty.
- **Bad (domain expert would flag):** A banner, pip progress line, `--json` report or blank line appears on stdout. A child consumes the client's `initialize` frame. Success is claimed from a test that wraps or filters stdout.
- **Stakes:** Critical.
- **Source:** MCP transports spec (re-fetched 2026-10-12, https://modelcontextprotocol.io/specification/2025-06-18/basic/transports): "The server **MUST NOT** write anything to its `stdout` that is not a valid MCP message", and the server "MAY write UTF-8 strings to its standard error". CONTEXT constraint "Stdio stdout stays protocol-only". Existing proof pattern `test_served_stdio_is_protocol_only_and_reads_the_owned_workspace`. WR-08 (docs promise `--json` on stdout).

**Dimension: Every checked-in skill and routine has exactly one predictable command**

- **Good (domain expert would accept):** `/omega-help` lists 46 entries: 12 curated (unchanged names and behaviour) plus 27 skills plus 7 routines. Names follow the collision rule, with the five known suffixed names. Each generated name parses and dispatches through `omega_command`. Skill commands return that skill's instructions. `onboard`/`python-clean`/`connectors` routine commands run the existing workflow. Other routines return their instructions. Two renders are byte-identical. Adding, renaming or editing a skill or routine, an orphan command file, a YAML-invalid skill, or a template↔disk mismatch fails `--check`.
- **Bad (domain expert would flag):** A collision drops or shadows an entry. A name is guessed fuzzily (`desk-lead` → `desk`). A curated command changes behaviour. `--check` passes while a committed file is stale. The generator writes files outside its owned set. A skill folder path is taken from user text.
- **Stakes:** High.
- **Source:** D-03, D-07, D-08, CONTEXT collision rule and resolved semantics. RESEARCH R-1..R-7 and §Generation rule. Repository catalog convention `tooling/catalog.py --check`. Cursor plugin reference (kebab-case `name`, `name`/`description` frontmatter; the official template validator rejects components missing them).

**Dimension: First start is repeatable and tells the operator what is wrong**

- **Good (domain expert would accept):** The root comes from the script's own location. One lock serializes concurrent starts. Installs use only `requirements-lock.txt` plus `--no-deps -e .`. A half-built venv is never stamped. A killed first start resumes on the next start. A warm start skips the install. Distinct exits name the cause: missing prerequisite, install failed, catalog drift, host unreachable. Only `prime-agent` is initialized, and `redteam` never is.
- **Bad (domain expert would flag):** The cwd walk selects another project. Two starts corrupt one venv. An unpinned `pip install -e '.[dev]'` runs at MCP start. Every failure is exit 1 or a hang. An interrupted install is stamped as done. The bootstrap initializes the T3MP3ST submodule.
- **Stakes:** High.
- **Source:** D-09, D-04, ROADMAP SC3, RESEARCH R-11/R-13/R-14 and §Bootstrap failure classes. MCP Security Best Practices: pin package versions instead of fetching latest at launch. OWASP Agentic Top 10 (ASI04 supply chain): pin dependencies. Hashes are absent from the lock today (RESEARCH Security Domain), recorded as a follow-up.

**Dimension: Claims match evidence; controls are not traded for convenience**

- **Good (domain expert would accept):** Docs and template distinguish what was proven locally (manifest validation, `--check`, real stdio `initialize` plus `tools/call` through the declared command from a fresh-clone layout, loopback HTTPS-entry verification) from what is confirmed by platform docs but unexercised (Command servers on the Bot computer, Remote HTTPS) and what is unverified user UAT (Grok Bot loading plugin skills/commands, a marketplace-declared stdio launch, `${CURSOR_PLUGIN_ROOT}` on Bot computers, the startup timeout, `"source": "./"` acceptance). `manifest.py` no longer claims a settings import. Approval-gated tools stay gated, the HTTPS host requires a bearer token, and the stdio host does not gain `--approve` or `--no-roster`.
- **Bad (domain expert would flag):** "Import into Grok Bot" is described as working. Plugin skills are said to appear in the `/` menu. A local model double or loopback host is called a live attachment. `--allow-insecure-no-auth` is suggested for the HTTPS route. A generated command calls a tool outside `registry.dispatch`. Native GSD is called signed Swarm approval.
- **Stakes:** Critical.
- **Source:** CONTEXT `<platform_facts>` and constraints. ROADMAP SC1 and SC4. RESEARCH P-1..P-15 and Assumptions A1..A10. Phase 77 evidence-boundary convention (`77-AI-SPEC.md` §1b). OWASP Agentic Top 10 ASI02/ASI03 (least privilege, explicit confirmation for destructive actions).

### Known Failure Modes in This Domain

1. **Credential leakage through launch configuration.** Committed `mcp.json` `env` values and command-line tokens are the most common MCP credential leak (OWASP MCP Security Cheat Sheet, MCP Security Best Practices). On a Grok Team Bot it also changes routing: a Command server with env or credential-looking args runs only in the owner's chat, so the "fix" silently breaks team use.
2. **Stdio framing corruption by setup tooling.** Package managers and git print to stdout, and interactive prompts read stdin. A server that installs itself on first launch is the classic way to violate the transport's stdout rule. It shows up as an opaque client "failed to start" or a hang, not as a readable error.
3. **Supply-chain and first-run drift.** Install at launch without pins (`npx -y`-style latest fetches), or a lock without hashes, lets a later start run different code from the one reviewed (OWASP Agentic ASI04, MCP Security Best Practices). Here the lock pins versions without hashes. The bootstrap must install only the lock, and hash pinning is a recorded follow-up, not in scope.
4. **Generated-surface drift and name confusion.** Generated command or skill sets drift from their sources, and look-alike or colliding names route a user to a different action than intended. This is the packaging analogue of tool-name typosquatting (OWASP Agentic ASI02). Here the known collisions are `python`, `onboard`, `connectors` and `ultrathink`, plus native `/python` versus `/omega-python` (RESEARCH pitfall 12).
5. **Over-claiming platform behaviour.** Packaging docs often promise marketplace or host behaviour from one vendor's documentation, while another product consumes it differently. Here Cursor documents plugin `commands`/`skills` and `${CURSOR_PLUGIN_ROOT}`, but no Grok Bot page documents loading them.

## 2. Framework Decision

**Selected Framework:** Existing custom Python packaging stack: the MCP Python SDK host already in the repo (`omega_prime.mcp_server`, stdio plus Streamable HTTP `/mcp`), the `omega_prime.commands` catalog and `omega_command` tool, Cursor Plugin manifests (declarative JSON and Markdown), the existing bash launcher extended with a bootstrap, a deterministic generator with `--check`, and pytest. No AI/LLM framework is added.

**Version:** Python `>=3.11` (`pyproject.toml:8`). Lock recorded on Python 3.12 (`requirements-lock.txt:1`): `mcp==2.3.0`, `pydantic==2.13.5`, `PyYAML==6.0.3`, `pytest==9.1.1`. Cursor Plugin format per https://cursor.com/docs/reference/plugins.md, re-fetched 2026-10-12. No dependency is added, removed or bumped.

**Rationale:** The phase wraps the existing core and does not rewrite it (CONTEXT domain boundary, D-04). Its failure modes are secrets, stream framing, deterministic generation, idempotent install and honest claims. Deterministic code checks catch all of them. A model-in-the-loop framework or a model judge would add provider calls, nondeterminism and secret surface without catching any of them. The Cursor Plugin format is the only manifest format that the confirmed import route (Cursor team marketplace → Grok Bot connector policy) reads, and the only one with a `commands` component (RESEARCH P-3a, State of the Art). The Bot-driven custom Command server path (D-06, primary) needs no manifest at all, just the same launcher command.

**Selector receipt (inline, auto mode; no interview because CONTEXT D-01..D-09 answer every selector question):**

```text
FRAMEWORK_RECOMMENDATION:
  primary: Existing custom Python + MCP Python SDK 2.3.0 host + Cursor Plugin manifests + bash bootstrap + pytest/generator --check

  hard_constraints: no new dependency; Python core only; no secret in manifest/argv/example/output; stdout protocol-only; auth/approval never weakened; live import is user UAT

```

**Alternatives Considered:**

| Framework | Ruled Out Because |
|-----------|------------------|
| Agent Plugins format (root `plugin.json`) | No `commands` component, and two manifests make format detection ambiguous (RESEARCH State of the Art; Recommended layout). |
| Project `.mcp.json` / `.grok/config.toml` | Grok Build CLI and Claude-compatible CLIs would auto-spawn the server whenever the repo opens (RESEARCH P-2). Nobody asked for that, and it is not evidence for the Grok Bot app. |
| A second (HTTPS) server in the shipped `mcp.json` | It would load for every installer and fail when unconfigured, and the token would have to become a plugin variable. Q7 resolved: HTTPS ships as docs plus a non-secret example only. |
| Wrapper skills per command (`disable-model-invocation: true`) | Declined by D-08: no wrapper skills. Routing goes through `omega-commands` + `omega_command`; plugin command files add palette entries where supported. |
| New agent/LLM or eval/tracing framework (LangChain, LangGraph, Phoenix, Promptfoo) | No inference capability is authorized. It would add provider calls, nondeterministic judgments and new secret and operational surface. |
| Python-side bootstrap inside `oneclick.py` | `oneclick.py` imports the package it would install at module load (`oneclick.py:34-49`), so it cannot create its own venv. Bootstrap must live in the shell wrapper (CONTEXT blockers). |

**Vendor Lock-In Accepted:** Partial. The secondary route uses Cursor's plugin format because that is how Grok Bot inherits team plugins. The primary route (D-06, a Bot-added custom Command server) and the core host stay format-neutral (plain stdio MCP and Streamable HTTP). No new runtime dependency on Cursor or xAI code.

### Common Pitfalls

1. **Hyphenated generated names do not parse today.** `_COMMAND_RE` stops at the first hyphen-less segment (`commands/__init__.py:25-28`), so `/omega-code-review` yields `not_a_command`. Widen the regex and add parser tests first. Otherwise every generated command fails even with a perfect catalog.
2. **The secret gate is path-sensitive and trips on the HTTPS header placeholder.** `assert_no_secrets(Path)` enforces mode 0600 before scanning (`grokbot/secret_guard.py:164-191`), so passing a committed 0644 manifest path raises `0600-violation`. Scan rendered **text** (`str`). Separately, a probe run on 2026-10-12 with `.venv/bin/python` showed `assert_no_secrets('{"headers": {"Authorization": "Bearer ${OMEGA_PRIME_MCP_TOKEN}"}}')` **trips** (`token-pattern`), and the `${env:…}` form trips too. The stdio args `${CURSOR_PLUGIN_ROOT}/omega_prime/scripts/grokbot-1click.sh …` and the path (B) command scan clean. So "run `assert_no_secrets` over every generated file" (RESEARCH drift check) fails on the HTTPS example as designed. Do **not** weaken the guard. Validate the single header value against an exact placeholder shape (`^Bearer \$\{(env:)?[A-Z][A-Z0-9_]*\}$`), replace that one validated value with a fixed sentinel, and gate the rest of the document unchanged. (Assumption AS-07.)
3. **The lenient repo parser hides platform rejection.** `parse_frontmatter` (`skills_runtime/guards.py:97`) accepts the 4 skills that `yaml.safe_load` rejects (an unquoted `: ` in `description`). Conformance must use `yaml.safe_load` plus `name == folder` plus non-empty `description` ≤ 1024. Keep the repo guard as well. PyYAML is transitive only, so the planner must either declare it or keep the import inside the check (AS-08).
4. **Stdout and stdin discipline belongs to the shell, not only to `oneclick`.** `oneclick` keeps its own text off stdout in served stdio (RESEARCH R-10), but the child host is spawned with inherited stdio (`oneclick.py:566-570`), and git/venv/pip print to stdout and may read stdin. Put `exec 3>&1 1>&2` at the top of the script, give every bootstrap child `</dev/null`, set `GIT_TERMINAL_PROMPT=0` and `PIP_NO_INPUT=1`, and restore fd 1 only on the final `exec`.
5. **Root and state come from cwd today.** The launcher walks up from `$(pwd)` (`omega_prime/scripts/grokbot-1click.sh:8-12`), and both `oneclick --root` and `mcp_server --root` default to `Path.cwd()` (`oneclick.py:880`, `mcp_server.py:1152`). Resolve `ROOT` from `BASH_SOURCE`, always pass `--root "$ROOT"`, and export `OMEGA_PRIME_STATE_DIR`/`OMEGA_PRIME_WORK_ROOT` defaults inside the script (never in `mcp.json`, because `env` restricts a Command server to the owner's chat). Fix WR-01 (stdio serve drops `--work-root`, `oneclick.py:566`) in the same change.
6. **Exit-class collisions.** `oneclick` already uses 0/1/2/3 (`oneclick.py:54-57`). New bootstrap classes must not reuse 1 or 3. RESEARCH recommends 10 `missing_prerequisite`, 11 `install_failed`, 12 `catalog_drift` and 13 `host_unreachable`, keeping 2 for usage.
7. **Routine-to-workflow mapping is by exact stem only.** Routine `desk-lead` is **not** workflow `desk` (RESEARCH R-3). A fuzzy mapping would silently execute a different sequence.
8. **Placeholder syntax differs by consumer.** A Cursor plugin uses `${VAR}`, a standalone Cursor `mcp.json` uses `${env:VAR}`, and Grok Build uses `${VAR}` (RESEARCH P-8). `${CURSOR_PLUGIN_ROOT}` expansion is confirmed for Cursor only.
9. **Symlink and exec-bit loss.** `scripts/grokbot-1click.sh` is a symlink (R-11). Declare `bash` plus the real path `omega_prime/scripts/grokbot-1click.sh`.
10. **`isolated_layout` is not a fresh-clone layout for the declared command.** It exports only the `omega_prime/` package subtree plus `omega_prime/ownership.yaml` (`local_validation.py:50,600-661`) and excludes `.venv` and `.git` (`:120`). The declared command needs root files the bootstrap reads: `pyproject.toml`, `requirements-lock.txt`, `.gitmodules`, `mcp.json` and `.cursor-plugin/`. A launcher run inside `layout.install` would therefore fail as `missing_prerequisite`/`install_failed` for the wrong reason. The SC5 proof needs a tracked-file tree with those root files, either an extended export profile or a copy driven by `git ls-files --recurse-submodules`, plus a warm venv provisioned so the stamp matches without network (AS-09).

## 4. Implementation Guidance

**Model Configuration:** **No model is selected or invoked.** Temperature, `max_tokens`, provider retries and judge settings do not apply. The Grok Bot's own model is an external consumer of the host. It reads tool descriptions, the `omega-commands` skill and command-file bodies, and nothing in this phase configures it.

**Core Pattern:** Generate deterministically, dispatch through the one tool, and bootstrap idempotently before serving.

1. **Generation (pure, deterministic).** Inputs in fixed order: curated `COMMANDS`; skills `sorted(p.parent.name for p in omega_prime/skills/*/SKILL.md)`; routines `sorted(p.stem for p in omega_prime/routines/*.md)`. The rule follows CONTEXT and matches RESEARCH:
   - `stem = source.removeprefix("omega-")`, `base = "omega-" + stem`. This gives `omega-commands` → `/omega-commands`.
   - Validate `base` against `^omega-[a-z0-9]+(?:-[a-z0-9]+)*$` with length ≤ 64. Abort generation on failure, naming the source path.
   - Curated names win. Every generated claimant of a base that equals a curated name, or that another generated entry shares, takes `-skill` or `-routine`.
   - Any remaining duplicate aborts generation, naming both sources. Nothing is dropped.
   - Expected today: `/omega-python-skill`, `/omega-onboard-routine`, `/omega-connectors-routine`, `/omega-ultrathink-skill`, `/omega-ultrathink-routine`. Total 12 + 27 + 7 = 46.
2. **Dispatch (CONTEXT resolved rule; differs from RESEARCH Q2's read-only recommendation, CONTEXT wins).** `execute_command` looks up the generated spec after the curated lookup and before `unknown_command`:
   - **Skill commands** return the skill instructions: `{"ok": true, "command": name, "result": {"kind": "skill", "source": "omega_prime/skills/<folder>/SKILL.md", "description": …, "instructions": <body after frontmatter>, "args": …}}`. Files are resolved only through the catalog key, never from user text.
   - **Routine commands whose exact stem is in `WORKFLOW_NAMES`** (`onboard`, `python-clean`, `connectors`) run that workflow through the existing `_workflow` → `run_workflow` path. That path dispatches through `registry.dispatch`, so approval gating is unchanged. `/omega-onboard-routine` and `/omega-python-clean` therefore execute the same sequences as `/omega-onboard` and `/omega-python`.
   - **All other routines** (`desk-lead`, `nightly`, `sweep`, `ultrathink`) return the routine pointer text as instructions, `kind: "routine"`. Their Python functions (`run_lead_pass`, `nightly_pass`, `sweep_mentions`, `resolve_turn_plan`) are **not** exposed. No new tool and no new approval surface is added.
   - Missing source file at runtime: `{"ok": false, "error": "source_missing"}` (or an equivalent explicit error). Never an empty success.
3. **Bootstrap then serve (D-09).** The shell extension runs these steps in order:
   - Script-relative `ROOT`, then `exec 3>&1 1>&2`.
   - Prerequisites (bash, git, python ≥ 3.11 with `venv`); missing → 10.
   - `git submodule update --init prime-agent </dev/null`, only when `$ROOT/.git` exists. A non-checkout gets a warning, not a failure. `redteam` is never initialized (D-04).
   - `flock` on `<venv>.lock`. If the stamp `{lock_sha256, pyproject_sha256, python, prime_agent_commit}` matches, skip the install and run only the import probe. Otherwise build a fresh venv in a temporary sibling, `pip install -r requirements-lock.txt` then `--no-deps -e .` with `</dev/null`, probe `import omega_prime, mcp`, atomically rename into place, and write the stamp last. Any failure → 11, with no stamp written.
   - Generator `--check` → 12 on drift.
   - `exec "$VENV/bin/python" -m omega_prime.grokbot.oneclick --root "$ROOT" --transport stdio … 1>&3 3>&-`.
   - An interrupted first start leaves no stamp, so the next start rebuilds safely (D-09 resume).
4. **HTTPS alternative (D-02).** Reuse `mcp_server --transport sse` with `--token-file` (a 0600 file) or `--token-env`, behind TLS, with `--public-url`. Point the Bot's Remote HTTPS server at `https://<host>/mcp` with the token held as a Bot secret. Ship only docs and `mcp.https.example.json` (not referenced by `plugin.json`). Resolve WR-02: the bearer token must not stay in the server process environment for the whole serve.

**Tool Use:** One rostered tool, `omega_command`, carries every curated and generated command. No family, roster or policy change (`omega_prime/contracts/tool-rosters/omega-prime.yaml`), so `tooling.catalog --check` output must stay byte-identical except for the updated `omega_command` description. Local proofs reuse the fresh-tree conventions of `isolated_layout` (extended or replaced for root files per Section 3 pitfall 10 and AS-09), the raw JSON-RPC stdio pattern of `test_served_stdio_is_protocol_only_and_reads_the_owned_workspace`, and `python -m omega_prime.grokbot.verify --url … [--transport http]` for the HTTPS entry.

**State Management:** The generator is stateless: inputs are checked-in files, outputs are committed files. Bootstrap state is the venv, the `<venv>.lock` sidecar and the completion stamp. The venv defaults to `$ROOT/.venv`, matching the current launcher precedence (AS-05). Host state stays out of the plugin root: the script exports `OMEGA_PRIME_STATE_DIR` (e.g. `${XDG_STATE_HOME:-$HOME/.local/state}/omega-prime`) and `OMEGA_PRIME_WORK_ROOT` (`/workspace` when it exists, else `$HOME`), but only when the caller has not set them. Skill frontmatter renames (`security-secrets-handling`, `security-supply-chain`) touch no stored state in the repository (RESEARCH Runtime State Inventory). A user's private Grok Bot skill library may still hold the old names; that is documented, not migrated.

**Context Window Strategy:** There is no model context in the delivered code. Downstream, the Bot model receives tool results. Skill-instruction loaders return the full checked-in body, never a truncated or summarized one; RESEARCH reports the longest skill *description* is 249 characters, and body sizes were not measured (AS-10). `/omega-help` grows from 12 to 46 rows of `name`/`usage`/`summary`/`when`. Keep the generated `when`/`summary` text one sentence, taken from frontmatter `description`, so the catalog stays small.

## 4b. AI Systems Best Practices

> Written inline in the `gsd-ai-researcher` role. It applies cross-cutting practice to a deterministic Code packaging phase. Where a model-specific practice does not apply, the section says so and explains why, following the Phase 77 exemplar.

### 4b.1 Structured Outputs with Pydantic

The structured outputs here are **generated artifacts and tool results**, not LLM answers: the `mcp.json` declaration and each generated catalog entry. Pydantic 2.13.5 is already in the lock. The repository uses dataclasses for `CommandSpec`. This instructional fixture adds no dependency, performs no network or file writes, and is syntax-checked only, not executed by this role. The planner may implement the same checks with dataclasses plus explicit validation, and the checks are what matter.

```python
from typing import Literal

from pydantic import BaseModel, ConfigDict, Field, ValidationError, field_validator

from omega_prime.grokbot.secret_guard import SecretLeakError, assert_no_secrets

NAME_PATTERN = r"^omega-[a-z0-9]+(?:-[a-z0-9]+)*$"
LAUNCHER = "${CURSOR_PLUGIN_ROOT}/omega_prime/scripts/grokbot-1click.sh"
EXPECTED_ARGS = [LAUNCHER, "--bootstrap", "--transport", "stdio"]


class StdioServer(BaseModel):
    # extra="forbid" rejects env, cwd, headers or url on the declared Command server.
    model_config = ConfigDict(strict=True, extra="forbid", frozen=True)

    type: Literal["stdio"]
    command: Literal["bash"]
    args: list[str]


class McpJson(BaseModel):
    model_config = ConfigDict(strict=True, extra="forbid", frozen=True)

    mcpServers: dict[str, StdioServer]


class GeneratedCommand(BaseModel):
    model_config = ConfigDict(strict=True, extra="forbid", frozen=True)

    name: str = Field(pattern=NAME_PATTERN, max_length=64)
    kind: Literal["curated", "skill", "routine"]
    action: Literal["builtin", "load_instructions", "run_workflow"]
    workflow: Literal["onboard", "python-clean", "connectors", "desk"] | None = None
    source: str = Field(min_length=1)
    description: str = Field(min_length=1, max_length=1024)

    @field_validator("source")
    @classmethod
    def _repo_relative(cls, value: str) -> str:
        if value.startswith("/") or "\\" in value or ".." in value.split("/"):
            raise ValueError("source must be repo-relative")
        return value


def validate_mcp_json(text: str) -> McpJson:
    doc = McpJson.model_validate_json(text)
    if list(doc.mcpServers) != ["omega-prime"]:
        raise ValueError("mcp.json must declare exactly the omega-prime server")
    if doc.mcpServers["omega-prime"].args != EXPECTED_ARGS:
        raise ValueError("declared stdio command drifted from the launcher contract")
    assert_no_secrets(text, name="mcp.json")  # str, never Path: a Path enforces 0600
    return doc


def validate_entry(raw: dict) -> GeneratedCommand:
    entry = GeneratedCommand.model_validate(raw)
    if (entry.action == "run_workflow") != (entry.workflow is not None):
        raise ValueError("workflow is set exactly when action is run_workflow")
    if entry.kind == "skill" and entry.action != "load_instructions":
        raise ValueError("skill commands load instructions only")
    return entry


fixture = (
    '{"mcpServers": {"omega-prime": {"type": "stdio", "command": "bash", '
    '"args": ["${CURSOR_PLUGIN_ROOT}/omega_prime/scripts/grokbot-1click.sh", '
    '"--bootstrap", "--transport", "stdio"]}}}'
)
try:
    validate_mcp_json(fixture)
    validate_entry(
        {
            "name": "omega-python-clean",
            "kind": "routine",
            "action": "run_workflow",
            "workflow": "python-clean",
            "source": "omega_prime/routines/python-clean.md",
            "description": "Run ruff then compileall through the python-clean workflow.",
        }
    )
except (ValidationError, ValueError, SecretLeakError):
    # Never print the exception: rejected input may carry the offending value.
    raise SystemExit("plugin contract rejected") from None
```

**Validation and retry policy:** Zero retries. A validation failure is a deterministic generator or `--check` failure (exit 1, or 12 when the bootstrap runs it), reported with the file path and a fixed rule identifier. Never print the rejected value. There is no `instructor`, `response_format`, `.with_structured_output()` or model repair loop, because no model produces these artifacts.

### 4b.2 Async-First Design

The MCP host is already async (`mcp_server._serve` → `stdio_server()` → `server.run`, `mcp_server.py:1145-1147`). This phase adds no async code. The generator and `--check` are synchronous CLIs, matching `tooling.catalog`. The bootstrap is bash that `exec`s the existing async host. The one mistake to avoid is wrapping the host in a Python bootstrap that calls `asyncio.run()` inside an existing loop, or that keeps a parent process piping stdio. The launcher must `exec`, so the MCP client talks directly to the host process. Streaming: the stdio protocol stream is the host's; bootstrap progress is line-buffered stderr only.

### 4b.3 Prompt Engineering Discipline

No inference prompt exists in the delivered code. The prompting **contract** is user-facing text read by the Grok Bot model: the `omega_command` description, `skills/omega-commands/SKILL.md`, generated `commands/omega-*.md` bodies, and the documented setup prompt. Keep them separated and directive:

- **Command-file bodies** say only: call the `omega_command` tool of the `omega-prime` server with `command` = `/omega-<x>` plus the user's arguments; do not reimplement the steps.
- **Setup prompt** (docs) tells the Bot to clone recursively into `/workspace/omega-prime`, run `bash …/grokbot-1click.sh --bootstrap-only` in its shell first, then add the custom Command server with the documented command.
- **Skill bodies** returned by loaders are checked-in data. Cursor and Grok Bot mark tool output as untrusted (RESEARCH Security Domain, cursor.com/docs/grok-bot/security.md).
- **`max_tokens` and few-shot** do not apply; no LLM call is authorized.

### 4b.4 Context Window Management

This is a Code system: completeness matters, not compaction. Never truncate, summarize or rerank a skill body or routine text returned by a loader. One-sentence catalog `summary`/`when` keeps `/omega-help` compact at 46 rows. If a future skill body grows large, the fix is editing the skill, not clipping it in the loader.

### 4b.5 Cost and Latency Budget

**Inference cost: zero calls and zero tokens** for every artifact and check in this phase. The relevant budget is the **first-start latency** on the Bot computer:

- The locked install is 146 `==` pins including `transformers==5.18.0`, `pyrit==1.1.0` and `numpy==2.5.3` (RESEARCH R-13).
- The Grok Bot MCP startup timeout is undocumented (RESEARCH P-12).
- Mitigations: a stamp-gated skip, so warm starts do only the import probe; a pre-run `--bootstrap-only` in the documented setup prompt; and an atomic venv build.
- No cold-install duration was measured, and none is claimed. The slow opt-in real-bootstrap test records one observation.
- Caching: exact-match only (stamp equality over lock, pyproject, interpreter and prime-agent commit). No semantic caching applies.
