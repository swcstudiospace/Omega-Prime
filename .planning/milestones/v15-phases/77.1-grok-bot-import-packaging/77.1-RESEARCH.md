## Summary

The import path the user expects does exist, but with a different shape and narrower availability than CONTEXT row 3 assumed. Cursor owns plugin distribution for Grok Bot, and there is no Grok-Bot-specific import field. **Import from Repo** is a Cursor dashboard action that creates a *team marketplace* (Dashboard → Plugins & MCPs → Team Marketplaces → Add Marketplace → Import from Repo). It is only available on Cursor Teams and Enterprise plans. Grok Bot inherits that team marketplace as its connector/plugin policy, and team-provided plugins appear in Grok Bot. The repository therefore needs a **Cursor Plugin**: `.cursor-plugin/plugin.json` plus `.cursor-plugin/marketplace.json` at the repo root, a root `mcp.json`, and component paths for `skills` and `commands`. Cursor documents every one of these primary sources. The Grok Bot docs never describe what Grok Bot does with a plugin's `skills/` or `commands/`. They describe plugins as connectors (MCP), and they document the `/` menu only for "saved skills". Native slash surfacing on Grok Bot is therefore unverified. The robust path is the existing prompting contract: a whole-message `/omega-<name>` is passed to the `omega_command` tool.

The stdio dispute is settled from a primary source. Grok Bot's Team Bot doc lists "Custom MCP server, **Command** | Runs on the computer each conversation uses". The enterprise doc refers to "`stdio` servers on the Bot's computer". So a stdio command server does run on the Bot's cloud computer. It is not limited to remote URLs. Two caveats apply. A Command server whose definition carries `env` or credential-looking arguments runs only in the owner's own chat. Nothing documents a client startup timeout, which matters for a bootstrap that installs 146 pinned packages. The HTTPS alternative maps to the documented "Remote HTTPS" custom server type. That type is the documented choice for servers that need secrets.

On the repository side, two blockers exist today. First, the command parser cannot parse any hyphenated generated name: `parse_omega_command("/omega-code-review")` returns `None`. Second, 7 of the 27 skills do not satisfy the Agent Skills / Cursor frontmatter contract: 4 fail YAML parsing, 1 has no frontmatter, and 2 have a `name` that differs from the folder. The existing launcher shell resolves the repo root from the current directory first, which is unsafe when a platform spawns it from an arbitrary cwd. The Python launcher (`oneclick.py`) already guarantees protocol-only stdout and has the right exit-code shape, but it cannot create its own venv because it imports the installed package. Bootstrap must therefore live in the shell wrapper.

**Primary recommendation:** Make the repository root a single Cursor Plugin named `omega-prime`. Generate `.cursor-plugin/{marketplace,plugin}.json`, `mcp.json` (stdio default only) and `omega_prime/grokbot/plugin/commands/omega-*.md` from one pure generator, with a catalog-style `--check`. Extend `omega_prime/scripts/grokbot-1click.sh` with a stdlib-only idempotent `--bootstrap` phase that keeps stdout clean before it `exec`s the existing `oneclick --transport stdio`. Ship the HTTPS entry as documentation plus a non-discovered example file. Widen `_COMMAND_RE` and resolve name collisions with a "curated wins, colliding generated entries take a kind suffix, otherwise fail" rule.

### Recommended layout (manifest file set)

```
.cursor-plugin/
  marketplace.json        # GENERATED. {"name":"omega-prime-marketplace","owner":{...},"plugins":[{"name":"omega-prime","source":"./",...}]}
  plugin.json             # GENERATED. {"name":"omega-prime","version":<pyproject version>,"description":...,"repository":...,
                          #   "skills":"omega_prime/skills","commands":"omega_prime/grokbot/plugin/commands","mcpServers":"mcp.json"}
mcp.json                  # GENERATED. stdio default only (see below). No env, no secrets.
omega_prime/grokbot/plugin/
  commands/omega-*.md     # GENERATED. One per catalog entry (12 curated + 34 generated = 46). Frontmatter name/description.
  mcp.https.example.json  # GENERATED. Documented HTTPS alternative; not named mcp.json and not referenced by plugin.json.
  __init__.py / render.py # generator + --check + --verify (placement: planner may choose omega_prime/grokbot/plugin.py)
omega_prime/commands/generated.py   # pure function: skills/routines dirs + curated COMMANDS → generated CommandSpecs
omega_prime/scripts/grokbot-1click.sh  # EXTENDED: script-relative root, --bootstrap phase, stdout discipline
```

The rationale for this layout:
- **Repo root = plugin root.** Then `${CURSOR_PLUGIN_ROOT}` is a checkout that contains the launcher, the lock and the package. That works for path (A) and is the same tree as path (B). Skills are referenced in place (`"skills": "omega_prime/skills"`), and per P-3a this replaces folder discovery. No copy means no drift.
- **Commands live in a subfolder** because the paths must be relative without `..` (P-15) and the root has no `commands/`.
- **`.cursor-plugin/marketplace.json` is included** because both official examples carry it and Import from Repo "re-reads the full manifest" (P-3). Using `"source": "./"` (repo-root plugin) has third-party corroboration only [ASSUMED]. The alternative that avoids that assumption is a `plugins/omega-prime/` subfolder, but its paths could not reach `omega_prime/` without `..`, which would force copying the skills. Record this as an Open Question if the planner prefers strict template conformance.
- **Not recommended:** a root `plugin.json` (Agent Plugin). The Agent Plugins format has no `commands` (reference table: "Agent Plugins … Skills, MCP servers"), and two manifests would make format detection ambiguous. Also not recommended: project-level `.mcp.json` or `.grok/config.toml`. They would make Grok Build/Claude-compatible CLIs auto-spawn the server whenever the repo is opened (P-2). Nobody asked for that, and it duplicates the roster surface.

### Stdio default entry (exact)

`mcp.json`:
```json
{
  "mcpServers": {
    "omega-prime": {
      "type": "stdio",
      "command": "bash",
      "args": ["${CURSOR_PLUGIN_ROOT}/omega_prime/scripts/grokbot-1click.sh", "--bootstrap", "--transport", "stdio"]
    }
  }
}
```
For path (B), the custom Command server takes the same command with an absolute path: `bash /workspace/omega-prime/omega_prime/scripts/grokbot-1click.sh --bootstrap --transport stdio`. A local fresh clone uses `bash <clone>/omega_prime/scripts/grokbot-1click.sh --bootstrap --transport stdio`.

Rules behind it:
- `type: "stdio"` is required by Cursor's table and by the Agent Plugins schema (P-9).
- Use `bash` explicitly because the executable bit and the `scripts/` symlink may not survive the platform's checkout. Point at the real file, `omega_prime/scripts/…`, not the symlink: Cursor documents that it skips symlinks that leave the plugin folder for local plugins [CITED: https://cursor.com/docs/plugins.md "Symlinks in `~/.cursor/plugins/local` load only when the target resolves to a directory inside that folder."].
- **No `env`, no `cwd`, nothing credential-shaped in args.** A Command server with env vars or credential-looking arguments is restricted to the owner's chat (P-4). The script resolves its own root from `BASH_SOURCE` and exports any internal defaults itself.
- Stdout discipline inside the script: at the top, `exec 3>&1 1>&2` (all bootstrap output goes to stderr). Every bootstrap child runs with `</dev/null`, because a child that reads stdin would swallow JSON-RPC frames. Set `GIT_TERMINAL_PROMPT=0` and `PIP_NO_INPUT=1`. The final step is `exec "$VENV_PY" -m omega_prime.grokbot.oneclick --root "$ROOT" --transport stdio "$@" 1>&3 3>&-`. `oneclick` already routes its own text to stderr in stdio mode (R-10).
- Root resolution: `ROOT` is derived from `realpath "${BASH_SOURCE[0]}"/../..` (the script's own location) and never from `$(pwd)`. This fixes R-11. The no-flag behaviour can stay as it is today for backward compatibility, provided the cwd walk is removed or demoted below the script location. The planner decides whether removing it is a clean cutover. Recommended: remove it, because script-relative resolution is strictly correct.

### HTTPS alternative entry

Documented, not auto-loaded. `omega_prime/grokbot/plugin/mcp.https.example.json`:
```json
{
  "mcpServers": {
    "omega-prime": {
      "url": "https://omega.example.com/mcp",
      "headers": { "Authorization": "Bearer ${OMEGA_PRIME_MCP_TOKEN}" }
    }
  }
}
```
- **Bot side:** add it as a Custom MCP server of type **Remote HTTPS**, with the token stored as a Bot secret (P-4: "For a custom server that needs secrets, choose **Remote HTTPS**"). Secret names must use "uppercase letters, digits, and underscores and start with a letter" [CITED: https://docs.x.ai/grok-bot/team-bots].
- **Docs must state the placeholder syntax per consumer (P-8):** `${VAR}` for a Cursor plugin variable or Grok config, `${env:VAR}` for a standalone Cursor `mcp.json`.
- **Host side:** reuse the existing documented SSE host (`.venv/bin/python -m omega_prime.mcp_server --transport sse --host … --port … --token-file <0600 file> --public-url https://…`). It already mounts Streamable HTTP at `/mcp` (R-12). Point the Bot at `/mcp`, not `/sse` (P-14).
- **Why not a second server in the shipped `mcp.json`:** it would load for every installer and fail when unconfigured. It would duplicate the tool surface, and as a Cursor plugin variable it would have to be declared in `variables` and be set by a team admin [CITED: https://cursor.com/docs/reference/plugins.md "Team admins set the actual values in the dashboard under **Plugins**"].
- **Local proof that it "resolves":** start a loopback host with `oneclick --self-test` or a spawned `--transport sse`, then run `python -m omega_prime.grokbot.verify --url http://127.0.0.1:<port>`. Also validate that the example file parses, has an `https://` URL and a `/mcp` path, uses only `${VAR}` placeholders and contains no literal token. A public host cannot be proven locally, so that part is UAT.

### Generation rule for `/omega-<name>`

Inputs, in deterministic order:
1. Curated `COMMANDS` (R-2), fixed.
2. Skills: `sorted(p.parent.name for p in omega_prime/skills/*/SKILL.md)`, keyed by **folder name**. That name is canonical in the template and prompts (R-5).
3. Routines: `sorted(p.stem for p in omega_prime/routines/*.md)`.

Rule:
1. `stem = source_name.removeprefix("omega-")` (this resolves `omega-commands` → `/omega-commands`, not `/omega-omega-commands`). `base = "omega-" + stem`.
2. Validate `base` against `^omega-[a-z0-9]+(?:-[a-z0-9]+)*$` and length ≤ 64 (the Agent Skills/Cursor kebab constraints). A failure aborts generation with the source path. Nothing is dropped.
3. A curated name always keeps its base name. If any **generated** entry's base equals a curated name, **or** two generated entries share a base, then **every generated claimant** of that base becomes `base + "-" + kind` (`-skill` / `-routine`).
4. After suffixing, any remaining duplicate or any clash with a curated name aborts generation, naming both sources.
5. The output is sorted by name, carries `kind`, `source` (repo-relative path) and `description`, and is byte-stable.

Applied to today's tree (46 total = 12 curated + 27 + 7):

| Source | Generated name |
|---|---|
| skill `python` (vs curated) | `/omega-python-skill` |
| routine `onboard` (vs curated) | `/omega-onboard-routine` |
| routine `connectors` (vs curated) | `/omega-connectors-routine` |
| skill `ultrathink` + routine `ultrathink` (**new collision**) | `/omega-ultrathink-skill`, `/omega-ultrathink-routine` |
| skill `omega-commands` | `/omega-commands` |
| routine `python-clean` | `/omega-python-clean` |
| routine `desk-lead`, `nightly`, `sweep` | `/omega-desk-lead`, `/omega-nightly`, `/omega-sweep` |
| the other 24 skills | `/omega-<folder>` (e.g. `/omega-code-review`, `/omega-security-secrets-handling`) |

**Execution semantics (recommended):** generated commands are **read-only instruction loaders** that run through `omega_command`. `execute_command("/omega-code-review …")` returns `{"ok": true, "command": "omega-code-review", "result": {"kind": "skill", "source": "omega_prime/skills/code-review/SKILL.md", "description": …, "instructions": <body after frontmatter>, "args": "…"}}`. A routine command returns the routine pointer text. For `onboard`, `connectors` and `python-clean`, that text already says "Run `/omega-…` through the `omega_command` tool", so the Bot executes the curated command next. Nothing executes twice, there is no new approval surface, and `run_lead_pass`/`sweep`/`nightly` are not exposed without approval gating. Files are resolved **only** through the generated catalog key, never from user text (no path traversal). `/omega-help` lists all 46 entries. Open Question Q2 records the alternative, where routine commands execute workflows directly.

**Required core change:** widen `_COMMAND_RE` to `^/(omega-[a-z0-9]+(?:-[a-z0-9]+)*)(?:\s+(\S[\s\S]*))?$` (R-1). Update the `omega_command` description and `omega-commands/SKILL.md` to name the generated classes.

### Drift `--check`

`python -m omega_prime.grokbot.plugin --check` follows catalog conventions (R-16): render to strings, compare byte-for-byte, write messages to stderr, and exit 1 on drift. `--write` (or `--out`) regenerates. It must fail on:
- any generated file differing from the committed copy (`.cursor-plugin/marketplace.json`, `.cursor-plugin/plugin.json`, `mcp.json`, `mcp.https.example.json`, each `commands/omega-*.md`);
- an **orphan** `commands/*.md` with no catalog entry;
- a skill whose frontmatter fails `yaml.safe_load`, lacks `name`/`description`, or has `name` ≠ folder (P-6, R-5);
- a naming collision or invalid name (generation rule step 2/4);
- a template ↔ disk mismatch in **either** direction (extends `lint_template`, R-8);
- a literal secret shape in any generated file (reuse `omega_prime.grokbot.secret_guard.assert_no_secrets`, imported in [VERIFIED: omega_prime/grokbot/verify.py:37]).

Wire it into `setup_check` and the CONTRIBUTING/`docs/setup.md` gate list. The shell bootstrap invokes it in step 12 (catalog_drift).

### Bootstrap / verify failure classes and idempotency

| Class | Exit | Trigger | Output |
|---|---|---|---|
| ok | 0 | ready; serve (stdio) or verify passed | stdio: nothing on stdout but protocol |
| usage/config | 2 | bad flags (existing `EXIT_CONFIG`) | stderr |
| missing_prerequisite | 10 | no `bash`/`git`/`python3 ≥ 3.11`/`venv` module; network unreachable for first install; `prime-agent` cannot be populated and is not a git checkout | one JSON line on stderr `{"class":"missing_prerequisite","missing":[…]}` |

| catalog_drift | 12 | generator `--check` exit 1 | stderr names the stale files |
| host_unreachable | 13 | `--verify`: spawned stdio `initialize` + `tools/call omega_command {"command":"/omega-help"}` fails or times out; HTTPS `verify --url` fails | stderr; `--verify --json` may print the report on stdout because verify mode is not a protocol stream |

These numbers are recommendations; the planner may choose others. They must not reuse 1/3, which `oneclick` already uses (R-10).

Idempotency:
- Hold an exclusive `flock` on `<venv>.lock` across the bootstrap (same convention as `oneclick._hold_launch_lock`, R-10).
- After success, write a stamp `<venv>/.omega-prime-bootstrap.json` = `{"lock_sha256", "pyproject_sha256", "python": "3.x.y", "prime_agent_commit"}`. A second run with an equal stamp skips the install and only runs the import probe, which is cheap and safe.
- A changed lock or Python version rebuilds into a fresh venv directory, then atomically renames it into place. A half-built venv is never stamped.
- Only `prime-agent` is populated (`git submodule update --init prime-agent`), never `redteam` (D-04, R-14). It runs only when `$ROOT/.git` exists. If `prime-agent` is not a checkout, the result is a stderr warning, not a failure, because Prime families are default-off. Whether the host really starts without it is [ASSUMED] and has its own test.
- Prefer `python3.12` (the lock's recorded interpreter), then `python3.11+` with a stderr warning (R-13).
- State goes outside the plugin root. The script exports `OMEGA_PRIME_STATE_DIR` and `OMEGA_PRIME_WORK_ROOT` defaults (e.g. `${XDG_STATE_HOME:-$HOME/.local/state}/omega-prime`, `/workspace` when it exists, else `$HOME`) **inside the script**, not in `mcp.json` (R-15, P-4).

## Common Pitfalls

1. **Generated names unparseable.** `_COMMAND_RE` accepts a single segment (R-1). Warning sign: `/omega-code-review` → `not_a_command`. Add parser tests first. *(Build-changing.)*
2. **Skills rejected by platform YAML.** 4 have an unquoted `: ` in `description`, 1 has no frontmatter, 2 have name ≠ folder (R-5). The repo's lenient line parser hides this. Validate with `yaml.safe_load` in `--check`. *(Build-changing: edits checked-in skills.)*
3. **Root picked from cwd.** The current wrapper walks up from `$(pwd)` (R-11), and a platform may spawn from any directory. Resolve from `BASH_SOURCE`.
4. **Stdout or stdin pollution during bootstrap.** pip, git and venv print to stdout, and any child reading stdin consumes protocol frames. Use `exec 3>&1 1>&2`, give every child `</dev/null`, and restore fd 1 only on the final `exec`.
5. **First-start timeout.** The locked install is 146 pins including `transformers` and `pyrit` (R-13), and the Grok Bot startup timeout is unknown (P-12). Make bootstrap idempotent and stamp-gated. Docs and the template's "First run" should tell the Bot to run `bash …/grokbot-1click.sh --bootstrap-only` (or `--verify`) in its shell **before** relying on the MCP server.
6. **Interpreter mismatch.** The lock was recorded on Python 3.12, and the Bot computer's Python is undocumented (P-10). A missing wheel surfaces as install_failed (11), not as a hang.
7. **State under a replaceable root.** The host writes `goals/`, `cron/`, the audit file and more under `--root` (R-14, R-15). The plugin root may be refreshed, and "manually installed packages" are replaceable (P-10). Export state and work-root defaults in the script.
8. **Team Bot Command restrictions.** `env` or credential-looking args restrict the server to the owner's chat (P-4). Keep `mcp.json` free of both.
9. **Placeholder syntax drift.** Cursor plugin `${VAR}`, Cursor standalone `${env:VAR}`, Grok `${VAR}` (P-8). The docs must show the right one per surface.
10. **Manifest path overrides discovery.** Setting `"skills"` stops scanning a root `skills/` (P-3a). That is intended here; nothing else should be expected to load.
11. **Symlinked script.** `scripts/grokbot-1click.sh` is a symlink (R-11). Reference the real path in `mcp.json`.
12. **Native `/python` vs `/omega-python`.** Plugin skills may surface natively as `/<skill-name>` (P-6, Cursor `/skill-name`), so the user can see both `/python` (skill instructions) and `/omega-python` (ruff + compileall). The prompting docs must explain the difference.
13. **Plan gating.** Import from Repo needs Cursor Teams/Enterprise (P-3). An individual-plan user needs path (B). *(Build-changing for docs and UAT; see Q1.)*
14. **Auto-refresh requires the Cursor GitHub App** (P-13). Without it, the marketplace stays at the imported commit until a manual **Refresh**, and generated files go stale on the platform even though `--check` passes locally.
15. **Doctor side effects.** Preflight writes an audit file under `--root` and FAILs on an empty `prime-agent` (R-14). That is non-fatal in stdio (strict off), but the planner should decide whether stdio serve passes `--skip-doctor` after bootstrap.
16. **`manifest.py` false claim.** "for direct import into Grok Bot settings" (R-8) contradicts P-3 and must be corrected so docs make no unproven claim.
