## Doctor semantics and limits

Use existing check IDs/category/message/fix-hint fields and existing `ok`, `warn`, `fail` serialization. Known disabled-by-default family should report PASS/ok with clear “disabled by configuration; execution not checked”; pending persisted schedule with family off or no inspectable runner is WARN with a nonexecuting remedy. A flag alone, installed scheduler library, or stored job is not proof of live delivery. Report “runner not observed by this diagnostic,” not “no runner running,” when cross-process state is unavailable. Include kind/count metadata, not prompt, result, history, or credentials. Preserve `--strict` semantics: WARN exits 1 in strict mode even though JSON `passed` can remain true. Existing doctor has other side effects (audit file append, registry/manifest inventory, possible RLM dirs/authorization); new family/schedule checks must be pure, and do not claim whole doctor is globally read-only.
