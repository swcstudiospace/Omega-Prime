# Phase 98-03 — Local-first retention

## Objective

Implement the complete shared retain operation and route only growth's shared-memory add path through it, preserving local-only profile and CRUD behavior.

## Context

Wave 2 depends only on completed `98-01` and runs independently from `98-02`. The frozen API, selector semantics, states, result envelope, validation, idempotency rules, security, and requirements live in `PLAN.md`; do not fork or amend those contracts here. Before implementation, confirm phase-97's `memory_write` signature/statuses and authoritative expected-version/idempotency semantics. If a required field/contract is missing or ambiguous, stop remote-write implementation and report the precise prerequisite gap; do not guess arguments or treat `None` as a wildcard. No edits to `tools/lead.py`, shared backend modules, or recall-owned consumers.

## Tasks

1. **Define and implement the retain operation.**
   - **Files:** `omega_prime/memory/retain.py`.
   - **Action:** Implement `retain_memory(...)` against the frozen `MemoryBackends` and backend types from 98-01. Append `graph_id=None` and `task_id=None` to the frozen API to preserve lead provenance separately from content/tags. Validate all request fields before IO; persist locally first and stop on local failure; then independently attempt every configured required remote destination. Include truthful `local_saved`, stable identity, refusal status and sanitized error. Bind operation identity to request and resolved destination; reject unsafe key reuse. Preserve exact local-entry dedup behavior and existing budgets.
   - **Verify:** Unit cases demonstrate validation-before-IO, local-first ordering, local-failure short circuit, destination participation, refusal/failure reporting and safe key reuse. Never leak credentials or raw exception detail.
   - **Done:** Complete typed result/error behavior matches the frozen shape and source states; phase-97 required expected-version handling is exact or explicitly blocked.
   - **Action detail:** Use 98-01's `encode_local_record`/`decode_local_record` helpers, with signatures `encode_local_record(record)->str` and `decode_local_record(stored_text, expected_bank)->LocalRecord|LegacyRecord`. Encoding returns the complete stored string: exactly one `[hindsight:<bank>] [omega-memory:v1]` wrapper plus compact sorted JSON with exactly `v=1, bank, scope, repo, kind, content, source, receipt_path, tags, graph_id, task_id`; content is canonicalized separately from evidence and JSON-escaped. Pass the complete encoded string directly to `MemoryStore.add("memory", encoded)`, never through `Hindsight.retain(encoded)` (which would double-wrap it). Decode takes the complete stored string, strips and validates the exact known outer bank envelope internally, then parses its inner marker/JSON and matches inner bank. Other banks are ineligible, not malformed; marker-free matching-bank legacy entries remain unscoped; recognized malformed versioned records fail. Search decoded content, not metadata, and hash only decoded canonical content. Reject `ENTRY_DELIMITER`; charge the complete wrapper/JSON/separators against the existing 2200-character memory budget (no budget increase). Keep operation UUID out of stored facts so exact local dedup remains unchanged.
   - **Ledger detail:** `MemoryBackends` owns the shared in-memory binding ledger. Generate one UUID per logical operation and store the binding before local mutation. Fingerprint canonical typed JSON for the full versioned record (including metadata/evidence), phase-97 `expected_version`, selected backend, and normalized effective write-destination identities (never credentials). A known ID is reusable only for identical fingerprint; reject mismatch before any local/network IO. An unknown caller-supplied ID—including after restart, recreation, or eviction—is refused before IO; never adopt it or silently mint a replacement. Retain the most recent 1024 completed bindings in LRU order; never evict in-flight entries. No TTL, session/time cap, journal, retry loop, queue, or background worker. Report UUID as `idempotency_key`; server/transport dedup remains only as strong as verified phase-97 support.
   - **Verify:** Separate invocations with the same bound caller ID reuse the key and avoid duplicate local facts; test mismatch of every fingerprint component before any write, and test unknown/restart/evicted IDs refuse safely. Test content/evidence/tags/graph/task bounds and serialized metadata overhead.
   - **Done:** API carries `graph_id` and `task_id` as separate stored metadata; ledger lifetime and refusal semantics are tested. No exactly-once guarantee is claimed for unsupported upstream behavior.
