# Plan 100-04: rpc-ui driver integration, caller propagation, operator control

Wave 4. Starts only after 100-02 and 100-03 have landed; all driver edits are
serialized behind this plan (100-01/100-02 finish their `omp_driver.py` work
first). Tasks sharing `test_engine.py` have one serial integration owner; the

Everything here is future execution instruction; nothing is complete now.

## Goal

Make rpc-ui asks operational end to end:

1. **Driver**: one single-owner event dispatcher for all child stdout across
  all wait phases; UI responses sent with the original external request id;
  pending human waits with no service-level deadline that stay abortable; the
  existing outer turn timeout remains Phase 97 scope; typed, exactly-once
  answer handling with job/session/turn/request identity.
2. **Callers**: `run()` gains an interaction context and a cancel token;
   `route_turn` runs rpc-ui when the agent carries an operator interaction
   context and an interrupt flag propagates after launch; every other `run()`
   caller is explicitly non-interactive with an honest surfaced outcome — no
   silent default-to-rpc production hole.
3. **Operator surface**: a smallest-operational local control plane plus
   `omega` CLI subcommands for pending-list/answer/abort that work while the
   conversation lease is held and while any MCP `ToolGate` slot is occupied.
4. **Visibility**: `ui_pending`/`ui_answered`/`ui_rejected_stale` (and
   `attached`/`attach_failed` from 100-01) rendered in `omega watch`, local
   status, and one doctor check; session result metadata survives final
   snapshots.
5. **Clarify cutover**: the echo clarify tool becomes the live service
   boundary (100-03's service) with every affected consumer updated; no echo
   fallback anywhere.

## Architecture decisions

### A. Single-owner event dispatcher (`omp_driver.py`)

Today three methods independently drain the shared stdout queue
(`wait_type`/`wait_response`/`_accept_prompt`, `omp_driver.py:158-199`,
`214-230`, `530-550`), so a UI request arriving during any other wait is
persisted but never dispatched, and concurrent consumers race for frames.
`_next` returns `None` both on queue timeout and on child EOF
(`omp_driver.py:214-230`, `_pump` `:233-239`), so a dead child is
indistinguishable from continued human waiting. `send` mints a fresh command
id and overlays fields (`:168-176`), which cannot carry an original external
request id.

The dispatcher is the only consumer of the pump queue for the whole session —
startup, command roundtrips, prompting, and pending-human periods. It:

- persists every frame (`append_event`) and tracks `agent_end`;
- routes `response`/`error` frames to the waiter registered for that command
  id, so `wait_response`, `read_until_agent_end`, `session_steer`, and
  `session_abort` become routed waits instead of competing consumers;
- routes subscribed UI request frames through 100-03's `parse_ui_request`
  into the live service (delivery, pending state, `ui_pending` event);
- distinguishes the pump's EOF sentinel from a queue timeout: EOF during a
  pending human wait is a terminal event — invalidate the request, end the
  run — never "keep waiting";
- serializes all stdin writes and control decisions (answer send, abort,
  cancel) under one lock so simultaneous operator answers and aborts cannot
  interleave;
- keeps pumping events and servicing abort the entire time a human answer is
  pending.

`send_ui_response(identity, value)` re-validates at the boundary, atomically
reserves `pending -> sending`, then attempts exactly one write of the
100-03-built response bearing the original external id. A successful write
transitions to `answered`; broken stdin/OSError transitions terminally to
`send_failed` and publishes `ui_send_failed`, never `ui_answered`. No retry or
duplicate frame. The dispatcher serializes answer, abort, invalidation and
send-failure races; the first reservation/terminal transition wins.

Pending UI answers have no separate service/registry deadline. The operator
override keeps Phase 97's existing `_TURN_TIMEOUT` and related arguments out
of scope; the current outer turn timeout may still end a prolonged ask until
Phase 97 is merged. Cancellation/abort, child EOF, broken stdin, or turn/session
end also terminate a pending wait. Do not add any timeout or cap.

Event subscription uses 100-03's observed per-mode `event_filter(mode)`.
Behavioral tests prove the actual subprocess receives rpc-ui events and does
not receive UI events in rpc; no constant equality or membership assertion
substitutes for that proof.

### B. Identity and persistence

Every UI request is bound to `(job_id, session generation, turn generation,
external request id)`. Host-owned opaque session/turn identifiers must be
freshly unique across process restarts, not resettable counters. Duplicate
requests deliver once; closed requests retain identity. Invalidation and send
reservation are serialized: whichever wins first determines the terminal
outcome; a write failure is terminal `send_failed`, never answered or retried.

`ui_pending`/`ui_answered`/`ui_rejected_stale` are durable redacted events via
the existing `append_event`/`write_json` path (`jobs.py:60-74`); `jobs.py`
itself is not modified. `attached`/`attach_failed` events come from 100-01's
discovery seam; this plan only consumes them. Preserve the already-acquired
`AcquiredAttachment` workspace owner through child exit; release only after
death/reap is proven.

**Session result metadata**: the success snapshot (`omp_driver.py:495-512`)
currently drops `mode`/`omp_major` written by the initial snapshot
(`:402-417`). The final `session.json` and `EngineResult` retain `mode`,
`omp_major`, attachment state, and UI lifecycle summary (requests seen,
answered, rejected stale, resolution); attachment/UI state is never erased by
the final rewrite.

### C. Caller propagation (no default-to-rpc hole)

`run()` receives an interaction context and cancel token. `rpc-ui` without a
safe context is an explicit error. At production composition, construct the
default live interaction/control context (not merely optional agent-attribute
injection): `OmegaPrimeAgent` construction in `omega_prime/agent/runtime.py`
and `default_registry`/coding-tool registration in `omega_prime/mcp_server.py`
must account for default callers and tool registration. The default
interactive `route_turn` uses this live context and selects `rpc-ui`; every
non-interactive caller is explicitly surfaced. Update all runtime/MCP
production registration/callers and prove this default path end-to-end, with
test-only injected contexts as separate deterministic protocol tests.

| Caller | Disposition |
| --- | --- |
| `attach.route_turn` | default production context uses rpc-ui and forwards interaction/cancel; explicit noninteractive agents surface `interaction: none` |
| delegate/desk/ultrathink callers | explicitly non-interactive rpc with honest outcome |
| runtime and `default_registry` composition | construct and register the production control/clarify context; no default path relies on tests manually setting an agent attribute |
`conversation_loop.run_conversation` checks `InterruptFlag` only before
entering `route_turn` (`conversation_loop.py:168`, `:192-205`) and holds the
session lease for the whole turn (`:157-189`). This plan forwards
`agent.interrupt` as the cancel token so a stop set after launch aborts the
running engine turn, and the operator reply/abort path is designed to need
**neither the conversation lease nor a second model turn** — answers go
through the control plane directly to the blocked `run()`. No change makes a
second ordinary conversation turn service the blocked one.

### D. Operator control surface (chosen: local control plane + `omega` CLI)

**Decision.** The smallest operational surface is a host-local control plane
written by the driver and driven by `omega` CLI subcommands:

 - `omega ui list [--job J]` — pending requests display the complete job/session/turn/request tuple.
- `omega ui answer --job J --session S --turn T --request R (--text …|--choice …|--confirm true|false)` — require every displayed identity field and preserve it unchanged through dispatch.
- `omega ui abort --job J --session S` — abort only the observed session.
- `omega ui status --job J` — local attachment state, pending/resolved requests and event tail.

New module `omega_prime/engine/ui_control.py`: control-record layout, atomic
writes (existing atomic-write helper), status/list/answer/abort entrypoints
shared by the CLI and the driver's control reader, so tests exercise the
production answer route, not a test-only callback. `omega_prime/engine/cli.py`
(currently watch-only, `cli.py:13-31`) gains the subcommands.

**Why not an MCP/registry tool or the HTTP admin surface.** `ToolGate`
serializes tool calls per registry (limit 1 by default) and a cancelled
caller keeps its slot (`mcp_server.py:1232-1255`); an engine turn blocking a
worker would queue any answer/abort tool behind the human wait — deadlock.
The authenticated admin-route pattern (`grokbot/approvals_api.py` guards,
`grokbot/security.py` `Principal`/scope checks, principal-bound HTTP sessions
in `grokbot/streamable.py`) is a good pattern but is **not** reused as this
phase's surface: the engine turn does not require a running HTTP host, and an
HTTP answer route would still have to avoid the gate. If a later phase adds
one, it must bind answers to an authenticated admin principal plus job
ownership, never payload-claimed identity, and must not import the approval
TTL/action model as UI-answer policy. No registry tool that can answer or
abort local omp UI is registered in this phase: ordinary model/tool output
must never become a human reply, and this plan creates no policy-answer
feature and weakens no connector approval — a confirm answer maps only to the
UI response frame and never touches the `ApprovalLog` or connector sends.

Authorization is possession of the host OS account able to write the private
control directory; ids are correlation handles, never authenticators. Before
interaction, resolve the control path and every effective writable bind
(work tree, job directory, omp home) and reject any overlap or unsafe symlink.
Private storage requires the expected uid and mode 0700 directory/0600 files,
no-follow, directory-descriptor-relative read/write/publication/release, and
durable staged inode before atomic no-replace publication. A read-only root
placement alone does not prove isolation. Unsandboxed execution, absent or
unproven mount isolation, or unsafe paths produce an explicit interaction stop
and honest undeliverable outcome; never a uid-warning fallback presented as
live human interaction. Require a provider-free real sandbox-denial smoke
before claiming trust isolation; fake controlled-human tests prove protocol
only. Driver child death/reap without proof preserves the interaction owner.
