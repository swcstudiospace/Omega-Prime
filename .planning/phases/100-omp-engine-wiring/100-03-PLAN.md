# Plan 100-03: UI protocol validation and live clarify service state machine

Wave 2. Runs in parallel with 100-01 (MCP) only on disjoint files. This plan
adds **no driver edits**: `omega_prime/engine/omp_driver.py`,
`omega_prime/engine/attach.py`, `omega_prime/agent/conversation_loop.py`, the

## Goal

Give Phase 100 the two engine-side halves of live HITL, so 100-04 only has to
wire them into the driver, callers, and operator surface:

1. **Protocol** (`omega_prime/engine/protocol.py`): validated
   `extension_ui_request`/`extension_ui_response` frame types built strictly
   from the fixture evidence 100-00 captures from the installed omp 18.8.4; a
   per-mode event filter so `rpc` behavior is unchanged while `rpc-ui`
   subscribes to UI requests; `max` added to accepted thinking levels (never
   `auto`).
2. **Service** (new `omega_prime/engine/hitl.py`): the live clarify service
   state machine — request normalization, the job/session/turn/request
   identity lifecycle with exactly-once answer reservation, stale/duplicate/
   invalid/unknown/wrong-identity rejection, terminal invalidation, typed
   answer validation per interaction kind, an `OperatorTransport` delivery
   boundary, and an explicit **undeliverable** outcome when no live transport
   exists. The question is never echoed back as an answer (there is no echo
   fallback).

## Design

### `omega_prime/engine/protocol.py`

- Add `max` to `THINKING_LEVELS`. Do not add `auto`; installed help lists it,
  the operator decision accepts only `max` (`100-CONTEXT.md` fixed decisions;
  ENG-100-06). The existing `_run` guard (`omp_driver.py:349-350`) enforces
  membership, so no driver edit is needed for acceptance; the full argv
  behavioral proof (`--thinking max` on a real run) belongs to 100-04's
  serialized driver task.
- Keep `EVENT_FILTER` (the `rpc` filter, `protocol.py:43`) unchanged and add a
  UI event set plus an explicit constructor such as
  `event_filter(mode: str) -> list[str]` returning `EVENT_FILTER` for `rpc`
  and `EVENT_FILTER` + the R4 UI event name(s) for `rpc-ui`. 100-04 switches
  the driver's `set_event_filter` call (`omp_driver.py:435-442`) to it; this
  plan only defines it and proves `rpc` output is byte-identical.
- Add request parsing/validation and response building against the R1–R3
  fixture shapes:
  - `parse_ui_request(frame) -> UiRequest | UiFrameError`: non-empty
    string-typed request id carried verbatim; known method only; method-specific
    prompt/options/schema present and well-typed; unknown methods, missing or
    empty or wrong-typed ids, missing prompts/options, and malformed schemas
    return `UiFrameError` with a stable reason. Malformed frames are never
    silently answered and never crash a caller.
  - `build_ui_response(request_id, value) -> dict`: one response frame bearing
    the **original external request id**, shaped per R2/R3.
- `loads` (`protocol.py:80-91`) keeps its tolerant behavior for non-object
  lines; UI validation is a separate explicit step so ordinary stream parsing
  is unchanged for 100-01/100-02 work.

### `omega_prime/engine/hitl.py` (new)

The live clarify service. It is host-side only and driver-agnostic so 100-04
can drive it from the single-owner dispatcher and register the clarify tool
against it.

 - Identity: every pending request is keyed by the four-part tuple
  `(job_id, session_generation, turn_generation, request_id)`. The external
  request id is preserved verbatim. Session and turn generations are host-owned
  opaque identifiers freshly unique across process restarts (for example,
  persisted random identifiers); resettable in-memory counters are forbidden.
  A reused job directory or repeated external id in a later run/turn cannot
  revive an old answer.
- Normalized request type carrying kind (ask/select/confirm per the observed
  vocabulary), prompt, offered options or request schema, and the identity
  tuple.
- `PendingRequestRegistry`, thread-safe (answers arrive from an operator path,
  invalidation from the reader/cancel path):
  - `open(...)` registers an incoming request exactly once. A duplicate
    incoming request (same tuple) does not deliver twice and does not create a
    second pending entry.
  - `submit(job, session, turn, request_id, value, responder)` validates then
    atomically reserves `pending -> sending` before the sole response write.
    Outcomes are typed: `accepted` (write succeeded), `rejected_stale`
    (terminal), `rejected_duplicate`, `rejected_unknown`, `rejected_identity`,
    `rejected_invalid`, `invalidated`, and `send_failed`. Invalid answers keep
    the request pending; only a validated answer reserves it.
  - `invalidate(...)` (single request, turn end, session end, cancel/abort,
    child exit/EOF, launch failure) moves affected requests to terminal states
    and retains closed-request identity. Invalidation wins if it lands first;
    an answer whose send reservation wins may complete exactly one write.
  - After the reserved write, success transitions `sending -> answered`;
    write failure transitions `sending -> send_failed`, terminalizes the
    request, publishes failure, and never retries or reports answered.
    Answer validation is performed immediately before reservation: ask answers
    satisfy observed R3 constraints; select answers match an offered identity/
    value; confirm answers are actual booleans.
  - `OperatorTransport.deliver(...)` is non-blocking. No registered transport
    or an undeliverable delivery terminalizes the request as undeliverable,
    with no response frame; it is not left pending indefinitely.
- No policy-file answer source is added anywhere in this service; a confirm
  outcome is data for the UI response only and can never approve sends,
  merges, or deploys.
